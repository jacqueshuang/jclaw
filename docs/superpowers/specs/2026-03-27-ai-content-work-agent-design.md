# AI 内容工作代理产品设计文档

- 日期：2026-03-27
- 状态：已确认设计，待进入实现规划
- 产品叙事：AI 内容工作代理
- 目标用户：个人高频使用者

## 1. 产品定义

这是一个面向个人高频使用者的通用 AI 自动化平台，但第一阶段不追求覆盖所有任务类型，而是聚焦于把复杂的研究整理型任务和内容成品生成型任务真正做完，并交付可直接使用的结果。

产品的核心价值不是聊天，不是展示 Agent 过程，也不是单纯做知识库，而是让用户通过对话交付一个目标后，系统自动整合公开网络与私有资料，调度内部多 Agent 完成研究、整理、沉淀与生成，最终交付可直接发送、发布或继续使用的成品。

## 2. 第一阶段定位

### 2.1 用户

第一阶段服务个人高频使用者，包括但不限于：
- 独立创作者
- 研究型工作者
- 产品经理
- 知识型内容生产者
- 需要持续整理资料并输出成品的人

### 2.2 主任务类型

第一阶段只重点支持两类任务：
- 研究整理型任务
- 内容成品生成型任务

### 2.3 默认工作流

标准工作流固定为：

**目标输入 → 研究整理 → 知识沉淀 → 内容交付**

系统不采用“直接生成后补研究”的默认策略，而是优先保证结果可用性与完成率。

## 3. 产品原则

### 3.1 任务完成率优先
系统设计优先服务于任务真正完成，而不是优先展示复杂能力。

### 3.2 最终结果优先
用户首先看到的是最终交付物，过程信息默认折叠，仅在需要时展开。

### 3.3 研究与生成分层
系统先形成结构化知识资产，再生成最终内容，避免直接生成导致内容空泛、失真或不可复用。

### 3.4 资料统一接入
公开网络与私有资料统一进入资料源体系，但不同来源的接入深度允许分阶段推进。

### 3.5 多 Agent 内隐化
系统内部支持多 Agent 并行分工，但对用户默认表现为一个主代理。

### 3.6 高风险动作显式授权
外部写操作或高风险行为必须经过用户授权后才能执行。

## 4. 核心模块

### 4.1 对话式任务入口
用户通过自然语言发起任务，可补充背景、受众、输出要求、约束和参考资料。

### 4.2 任务编排引擎
负责理解目标、拆解步骤、判断资料需求、调度子代理、控制任务生命周期。

### 4.3 统一资料源层
统一管理公开网页与检索结果、上传文件与粘贴文本、云文档/知识库连接、本地目录型来源。

### 4.4 知识沉淀层
将研究结果整理为可复用的 Knowledge Pack，而不是只保留聊天过程。

### 4.5 结果交付层
以 Deliverable 为核心对象，对外输出以下结果：
- 内容成品
- 可执行方案 / 计划文档
- 整理后的资料集

### 4.6 账户与订阅系统
第一阶段平台层优先建设账户体系与订阅计费能力，支持个人商业化闭环。

## 5. 核心对象模型

### 5.1 Workspace
承载长期上下文的工作空间，包含资料、任务、知识资产与交付结果。

### 5.2 Task
用户发起的一次具体委托，是系统运行的主线对象。

### 5.3 Source
所有任务输入资料的统一抽象，覆盖公开与私有来源。

### 5.4 Knowledge Pack
研究阶段沉淀出的结构化知识资产，可被后续任务复用。

### 5.5 Deliverable
任务最终交付物，是判定“完成”的核心对象。

## 6. 核心任务流

### 6.1 目标输入
用户通过对话输入目标，并可附带背景、目标受众、输出形式、限制条件和参考资料。系统将自然语言目标整理成内部任务卡。

### 6.2 任务理解与拆解
系统识别任务类型、资料需求、是否需要访问外部来源、是否需要用户授权外部动作，以及最终交付物目标。仅在必要时追问。

### 6.3 资料收集与整理
系统收集公开网络资料、用户提供资料以及工作空间中的历史知识资产，并完成去重、归类、摘要与关联。

### 6.4 知识沉淀
系统将研究结果整理为 Knowledge Pack，使研究与生成解耦，提升可复用性和结果稳定性。

### 6.5 结果生成
基于 Knowledge Pack 生成最终交付物，允许内部多轮迭代，但默认只向用户呈现关键版本。

### 6.6 结果交付与归档
系统展示最终交付物、简要说明、可展开的过程摘要、相关知识包与参考来源，并将结果沉淀回 Workspace 供后续复用。

## 7. 多 Agent 架构

第一阶段采用“1 个主代理 + 3 类子代理”的结构。

### 7.1 Orchestrator
主代理，负责理解用户目标、生成执行计划、决定是否调用子代理、汇总中间结果并形成最终交付。

### 7.2 Research Agent
负责搜集公开资料、读取私有材料、提取关键信息并形成结构化研究摘要。

### 7.3 Synthesis Agent
负责多来源资料整合、去重、分类、抽象与 Knowledge Pack 构建。

### 7.4 Delivery Agent
负责将知识资产转化为内容成品、方案文档或整理后的资料结果。

对用户默认不强调角色分工，只在需要时展示执行细节。

## 8. 资料接入策略

### 8.1 产品层策略
采用统一资料入口，让用户理解为“把资料交给系统”。

### 8.2 能力层优先级

#### 第一优先级
- 上传文件
- 粘贴文本
- 网页链接
- 基础公开检索

#### 第二优先级
- 云知识库 / 云文档连接

#### 第三优先级
- 本地目录 / 持续同步型来源

产品层面统一建模，能力层面分层落地，不要求所有资料类型首发同深度支持。

## 9. 结果交付结构

任务完成页建议按以下层次组织：

### 9.1 Final Deliverable
直接展示最终内容成品或最终文档。

### 9.2 What Was Done
用极简摘要说明研究主题、资料来源与产出内容。

### 9.3 Supporting Assets
挂载相关 Knowledge Pack、参考来源、中间摘要和可继续迭代的结果版本。

### 9.4 Execution Trace
默认折叠，仅在需要时展开，展示执行步骤、参与 Agent、授权动作与不确定项。

## 10. 异常处理机制

### 10.1 自动补足
适用于低风险缺口，例如输出格式未明确但可采用默认模板。

### 10.2 带假设继续执行
适用于中风险缺口，例如风格、长度、表达倾向未明确。系统记录采用的假设，并允许后续快速修正。

### 10.3 必须中断确认
适用于高风险节点，例如外部写操作、关键资料不足、目标歧义过大、涉及权限或敏感边界等。

## 11. 质量控制机制

系统内置四道质量关：

1. 任务定义校验
2. 研究材料校验
3. 交付物可用性校验
4. 结果与目标对齐校验

质量控制目标是防止流程结束但结果不可用。

## 12. 状态模型

第一阶段保留最小状态集合：
- 已接收
- 研究中
- 整理中
- 生成中
- 已交付

补充异常状态：
- 等待确认
- 交付受阻

状态设计目标是建立用户信任，而不是展示底层系统复杂度。

## 13. 完成判定

只有同时满足以下条件，任务才可判定为完成：

1. 已形成明确 Deliverable
2. Deliverable 与原任务目标直接对应
3. Deliverable 达到可直接使用标准
4. 关键缺失已解决或被明确说明
5. 用户无需大量二次加工即可继续使用

若只完成研究、只生成草稿，或关键资料缺失导致结果不可用，则仅能判定为部分完成。

## 14. 测试策略

### 14.1 任务闭环测试
验证目标输入、资料接入、研究整理、知识沉淀与结果交付能否完整跑通。

### 14.2 资料混合测试
验证公开资料与私有资料混用时是否能正确整合、关联并反映到最终结果中。

### 14.3 交付物可用性测试
验证最终结果是否结构完整、可直接使用、无需大量返工。

### 14.4 中断与恢复测试
验证权限确认、信息补充、失败恢复和重新执行能力。

## 15. MVP 指标

### 15.1 任务完成率
最终成功交付可用结果的任务数 / 发起任务总数。

### 15.2 一次交付可用率
无需大幅返工即可使用的交付结果占比。

### 15.3 资料利用有效率
衡量交付物是否真正使用了公开资料与私有资料，而非表面接入。

### 15.4 任务复用率
衡量历史 Knowledge Pack、资料和交付结果是否被后续任务复用。

## 16. 第一阶段不做重点

为保证范围收敛，第一阶段不将以下方向作为首发重点：
- 强调 Agent 可视化协作界面
- 覆盖过多任务类型
- 一开始把所有资料连接器做深
- 优先做复杂团队协作
- 优先做重企业权限与审计体系
- 把产品做成知识库工具而不是任务完成平台

## 17. 对外品牌叙事

第一阶段外部品牌叙事定义为：

**AI 内容工作代理**

推荐一句话介绍：

> 一个结果导向的 AI 内容工作代理，能结合公开网络与私有资料，自动完成研究、整理，并交付可直接发布的内容成品。

扩展版介绍：

> 它通过对话接收目标，自动整合公开信息与用户资料，内部调度多 Agent 完成研究、知识沉淀与内容生成，最终输出可直接使用的内容成品、执行方案和资料包。

## 18. 总结

这是一个以“结果交付”为核心的个人 AI 内容工作代理产品。第一阶段通过收窄任务范围、统一资料源建模、强化知识沉淀、隐藏多 Agent 复杂度，并以 Deliverable 作为完成标准，建立任务完成平台的基本竞争力。后续扩展应建立在任务闭环能力已经跑通的前提之上，而不是提前扩张任务类型或平台复杂度。
